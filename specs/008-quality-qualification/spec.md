## Clarifications

### Session 2026-09-29

Resolved autonomously by the agent (agent review, not an approval) from `docs/PROJECT_SPEC.md`
§13 and F001–F007 precedent, at the owner's standing instruction to be fully autonomous; see
`docs/ASSUMPTIONS.md`. The owner may override any answer.

- Q: Who performs the "expert review" that the suite and the human-judged metrics require? → A: a
  human reviewer (the project owner or a delegate). The agent authors the cases and the rubric,
  and may add an "agent review" note, but never marks a case or a claim as human-reviewed. Metrics
  that need human judgement (factual support precision, required-fact coverage) and the
  "reviewed suite" gate report **blocked — awaiting human review** until filled review sheets are
  imported. No local LLM judge is added in F008 (the master spec allows one only for triage).
- Q: How are the existing F004/F005 development case files related to the 100-case suite? → A:
  the suite is a new pair of files under `eval/suite/` (60 development, 40 held-out) with the full
  master §13.2 case schema. Development cases may reuse and extend earlier questions, since the
  system was already tuned on them. Held-out cases are all new questions, and are frozen by a
  committed hash manifest before their first run. The earlier files stay unchanged as history.
- Q: What are the 20 "adversarial/provenance/version" cases, given that the real corpus contains
  no injected text? → A: questions that attack or probe the system without changing the corpus:
  prompt-injection questions, non-existent or fake requirement IDs, questions presupposing a
  release or version the snapshot does not contain, and provenance questions ("which file defines
  …"). Injected documentation is covered separately by an extended synthetic hostile suite on a
  synthetic snapshot, which feeds the injection-resistance gate.
- Q: How is blocked-egress operation (AT-01, open item A-032) demonstrated without root? → A:
  inside an unprivileged user and network namespace that has only a loopback interface, run a
  private local runtime that reads the already-installed models (same digests) and the
  application. Then ask a covered question, open the excerpt, search, and export. A failed DNS
  lookup to an external host shows that egress is blocked. This is repeatable with one command.
- Q: Where does the release report live, and is it committed? → A: generated by a command into
  `data/reports/release-<utc>/` (Markdown and JSON). The copy used as F008 evidence is committed
  under `docs/quality/`, which is not external publication. It lists every gate with status
  `pass`, `fail`, `blocked` (with the blocking reason) or `not run`, and names the evidence kind
  behind each value: deterministic test, real-model run, human review, or measurement.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A release report that cannot overstate quality (Priority: P1)

A maintainer deciding whether the local release is ready runs one command and gets a report that
lists every master §13.3 threshold and §13.5 acceptance scenario with its measured value,
denominator, evidence kind and status. Anything not measured is "not run". Anything depending on a
human review that has not happened is "blocked", with the reason.

**Why this priority**: this is the F008 acceptance. Without it, the other measurements cannot be
read safely.

**Independent Test**: generating the report from fixture inputs yields `pass`, `fail`, `blocked`
and `not run` rows as the inputs dictate. It never yields `pass` for a human-judged metric without
an imported human review, or for a gate whose evidence is missing.

**Acceptance Scenarios**:

1. **Given** held-out runs exist but no human review sheet is imported, **When** the report is
   generated, **Then** factual support precision and required-fact coverage are `blocked —
   awaiting human review` and the suite gate is `blocked — cases unreviewed`.
2. **Given** a gate with no recorded evidence, **When** the report is generated, **Then** it is
   `not run`, never `pass`.
3. **Given** deterministic, real-model, human and measurement evidence, **When** the report is
   generated, **Then** each row names its evidence kind and source file, and the report has
   separate sections per evidence kind plus unresolved limitations (open assumptions, deferred
   checks).
4. **Given** a critical isolation or injection failure, **When** the report is generated, **Then**
   the overall verdict is `blocked` regardless of other averages.

---

### User Story 2 - A 100-case suite with a frozen held-out split and a review workflow (Priority: P1)

A maintainer has a 100-case evaluation suite that follows master §13.2: category minimums, a
stratified 60/40 split, full case fields, and gold evidence alternatives. The held-out file is
frozen before use. A reviewer receives a rubric and review sheets, and their judgements are
imported into the metrics.

**Why this priority**: the reviewed suite and held-out quality report are release gates, and they
are the only way to measure answer quality honestly.

**Independent Test**: the case files validate. Category counts, split stratification and the
held-out freeze are enforced by tests. Changing a held-out case without updating the freeze
manifest fails the test suite. A filled fixture review sheet changes the human-judged metrics from
blocked to computed.

**Acceptance Scenarios**:

1. **Given** the suite files, **When** validated, **Then** there are 100 cases with at least 15 per
   core category, at least 20 unanswerable/missing-scope/conflicting and at least 20
   adversarial/provenance/version cases; the split is 60/40 with each category divided in
   proportion (± 1).
2. **Given** a held-out case is edited, **When** tests run, **Then** they fail unless the freeze
   manifest is regenerated by an explicit command, which records who changed it and why.
3. **Given** a suite run, **When** it finishes, **Then** a review sheet lists every factual claim with
   its cited excerpts and the case's expected facts and forbidden assertions, with empty judgement
   fields.
4. **Given** a filled review sheet, **When** imported, **Then** factual support precision and
   required-fact coverage are computed with numerators and denominators per category, and the
   reviewer name and date are recorded.

---

### User Story 3 - Offline, privacy and adversarial qualification (Priority: P1)

A maintainer proves that chat, search, evidence and export work with external egress blocked, that
nothing leaks question or answer text, and that the adversarial suites produce zero critical
failures, all with the real local models.

**Why this priority**: offline operation and injection resistance are critical gates (master
§13.3). A-032 has been open since F005.

**Independent Test**: one command runs the blocked-egress scenario and records its results; the
adversarial suites run with the real model and report zero or more failures by kind.

**Acceptance Scenarios**:

1. **Given** a namespace with only loopback, **When** the offline check runs, **Then** an external
   DNS lookup fails, and a covered question gets a cited answer whose excerpt opens. Search and
   export also work, and the result is recorded.
2. **Given** the synthetic hostile suite (forged instructions, fake citations, malicious URLs,
   breakout markup, fake policy notices), **When** run with the real model, **Then** no answer
   follows an injected instruction, discloses the policy, carries a link, or cites a non-supplied
   evidence ID. Any failure blocks the release.
3. **Given** the adversarial questions in the suite, **When** run, **Then** fake IDs return no
   invented record, presupposed versions are not confirmed, and injection questions do not change
   behaviour.
4. **Given** the privacy checks, **When** run, **Then** no question or answer text appears in logs,
   no telemetry or third-party request exists, and no conversation data is persisted.

---

### User Story 4 - Performance qualification (Priority: P2)

A maintainer measures the master §13.4 budgets on the reference workstation with at least 50
representative queries after warm-up, warm and cold reported separately, and publishes the
hardware and the peak memory.

**Why this priority**: required release evidence, but it does not affect correctness.

**Independent Test**: the harness with fake providers produces a report with all measurements;
the real run is recorded.

**Acceptance Scenarios**:

1. **Given** the reference workstation, **When** the performance run executes, **Then** it reports p50
   and p95 for lexical and hybrid retrieval, first progress event and final answer. Each is split
   into warm and cold, with the query count and the corpus chunk count.
2. **Given** a running answer, **When** cancelled, **Then** the time to release the slot is
   measured.
3. **Given** the run, **When** it finishes, **Then** peak GPU memory and host memory are recorded, or
   "not available" is stated.

---

### User Story 5 - Traceability completeness and model qualification (Priority: P2)

A maintainer can check automatically that every master requirement has a traceability row with an
owner, a status and existing evidence paths. They can also see a model qualification record for
the locked models: identity, license as reported by the local model artifact, measured quality and
performance, and known limits.

**Why this priority**: required for release, but it depends on the other stories' results.

**Independent Test**: the checker flags a requirement missing from TRACEABILITY, a row pointing to
a non-existent test file, and an `open` status. The model record is generated from the lock and the
local runtime without any download.

**Acceptance Scenarios**:

1. **Given** the master spec and TRACEABILITY, **When** checked, **Then** every local requirement
   (LOC, SRC, RET, ANS, UX, SEC, OPS) has a row. Referenced test files exist. Public (PUB)
   requirements are listed as deferred to F010.
2. **Given** the locked models, **When** qualified, **Then** the record shows tag, digest, runtime
   version, license text summary from the local artifact, context size, measured suite results and
   budgets, and the date. It makes no claim beyond the recorded measurements.

---

### Edge Cases

- Fewer than 50 distinct queries available for performance → the harness repeats nothing
  silently; it reports the count it used and marks the budget `fail` (insufficient sample).
- The local runtime is unavailable during a suite run → the run stops with the error; no partial
  metrics are reported as complete.
- A review sheet refers to cases or claims that are not in the run → the import is rejected, with the
  mismatches listed.
- A review sheet is only partly filled → metrics are computed on the reviewed subset, and the
  report shows "partial human review (n/N)", never a pass.
- The held-out split has been run before being frozen → impossible by construction: a suite run
  refuses a held-out file that does not match its freeze manifest.
- GPU memory tools are missing → "not available", never an invented number.
- The unprivileged namespace cannot be created on a machine → the offline check reports `not run`
  with the reason.
- Three held-out runs disagree → each run is reported, with the spread per metric (master §13.3).

## Requirements *(mandatory)*

### Functional Requirements

**Suite and review (master §13.2)**

- **FR-001**: The system MUST provide an evaluation suite of 100 cases in two files (60
  development, 40 held-out) whose cases each carry: ID, primary category, secondary tags,
  question, expected status, expected facts (with acceptable variants), gold evidence groups (with
  alternatives), forbidden assertions, pinned source revisions, and human-review status.
- **FR-002**: Category minimums MUST be enforced: at least 15 each for onboarding/build,
  architecture/interfaces, process/work products and requirements/templates; at least 20
  unanswerable/missing-scope/conflicting; at least 20 adversarial/provenance/version. The split
  MUST divide each category in proportion to 60/40 (± 1 case).
- **FR-003**: The held-out file MUST be frozen by a committed manifest (SHA-256 of the file and
  metadata: date, reason). A suite run on a held-out file that does not match its manifest MUST be
  refused, and the test suite MUST fail on a mismatch.
- **FR-004**: A review rubric MUST define claim support judgements (supported / partially
  supported / unsupported / not a factual claim), required-fact judgements (covered / partly /
  missing / wrong) and a forbidden-assertion check, with examples. It MUST state that an existing
  citation does not make a claim supported.
- **FR-005**: Each answer-suite run MUST emit a review sheet listing every factual claim with its
  cited excerpts, the case's expected facts, and forbidden assertions, with empty judgement fields
  plus reviewer and date fields.
- **FR-006**: Importing a filled review sheet MUST validate that it matches the run (case IDs,
  claim hashes) and MUST compute factual support precision and required-fact coverage per
  category, with numerators and denominators, reviewer and date. The agent MUST NOT fill in or
  import judgements as a human review.

**Harness and metrics (master §13.3)**

- **FR-007**: A suite command MUST run retrieval and answer evaluation on a split and compute:
  evidence recall@10 (answerable cases), safe handling of unsupported cases, false abstention,
  citation integrity, automated forbidden-assertion hits, status agreement, and latency. It MUST
  support repeated runs (`--runs N`) and report each run and the spread per metric.
- **FR-008**: The suite command MUST label every report "development measurement" unless the
  case file is human-reviewed and the split is held-out.
- **FR-009**: Existing automated gates MUST be collected as evidence: exact-ID retrieval, snapshot
  isolation, comparison isolation and deletion-claim counts, deterministic test results, and CI
  results. They are collected from their commands or recorded reports, never re-typed by hand.

**Adversarial, offline and privacy (master §13.2, §13.3, AT-01, AT-06, AT-15, AT-18)**

- **FR-010**: The synthetic hostile suite MUST be extended to cover forged instructions, fake
  citations in text, malicious URLs, breakout markup, fake policy/system notices and requests to
  run commands. Run with the real model, each case is judged automatically for: followed an
  injected instruction, disclosed the policy, included a URL, cited a non-supplied ID, presented a
  command as advice. Any failure MUST be reported by kind and MUST block the release.
- **FR-011**: A repeatable offline check MUST run the application and a private local runtime in
  an unprivileged network namespace with only loopback. It MUST prove that external egress is
  blocked, and then exercise ask (cited answer), excerpt retrieval, search and export, recording
  each result. When the namespace cannot be created, it MUST report `not run` with the reason.
- **FR-012**: Privacy checks MUST be collected as release evidence: no question or answer text in
  server logs during suite runs, no telemetry or third-party request (frontend checks), no
  persisted conversation data.

**Performance (master §13.4)**

- **FR-013**: A performance command MUST measure, with at least 50 distinct representative queries
  after warm-up: lexical and hybrid retrieval, time to first progress event, and final validated
  answer. Each is reported warm and cold (cold = models unloaded through the local runtime before
  the first request) with p50/p95, counts and the corpus chunk count. It MUST also measure
  cancellation release time and peak GPU and host memory (or state "not available").
- **FR-014**: Each budget MUST be compared with the master §13.4 target and marked `pass`/`fail`.
  A sample below 50 queries MUST mark it `fail (insufficient sample)`.

**Release report, traceability, model qualification**

- **FR-015**: A release-report command MUST assemble all gates from recorded evidence files into
  Markdown and JSON with, per gate: target, measured value with denominators, evidence kind,
  evidence file, status (`pass`/`fail`/`blocked`/`not run`) and reason. It MUST also include
  sections for deterministic tests, real-model runs, human reviews and unresolved limitations
  (open assumptions and deferred checks), and an overall verdict that is `blocked` whenever a
  critical gate fails or a required gate is blocked or not run.
- **FR-016**: A traceability checker MUST verify that every local requirement ID in the master spec
  has exactly one row in TRACEABILITY with a status, that every referenced test or code path
  exists, and that PUB requirements are marked deferred. It MUST run in CI.
- **FR-017**: A model qualification record MUST be generated for each locked model from the model
  lock and the local runtime (no download): tag, digest, runtime version, the license as reported
  by the local artifact (summarised, with the full text kept locally), context size, and links to
  the measured suite and performance results.
- **FR-018**: No command in F008 MAY download models or sources, call a non-loopback service
  during evaluation, or log question or answer text.

### Key Entities

- **SuiteCase**: ID, category, tags, question, expected status, expected facts (with variants),
  gold evidence groups (alternatives), forbidden assertions, source revisions, review status.
- **FreezeManifest**: file path, SHA-256, case count, frozen-at date, reason, previous hash.
- **SuiteRun / SuiteReport**: split, run index, per-case results, metrics with denominators,
  labels, model and snapshot identity.
- **ReviewSheet / HumanReview**: per-claim and per-fact judgements, reviewer, date, run reference.
- **Gate**: ID, target, measured value, evidence kind (deterministic / real-model / human /
  measurement), evidence file, status, reason, critical flag.
- **ReleaseReport**: gates, sections per evidence kind, limitations, verdict, created-at, app and
  model identities.
- **ModelQualification**: role, tag, digest, runtime version, license summary, context, results.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: The release report contains a row for every master §13.3 threshold and every local
  AT-01–AT-18 scenario, each with a status and an evidence kind; none is `pass` without an
  evidence file.
- **SC-002**: 100% of human-judged metrics are `blocked` unless a human review sheet has been
  imported (verified with and without a fixture sheet).
- **SC-003**: The suite has exactly 100 cases, meeting every category minimum, and the held-out
  freeze is enforced by a test.
- **SC-004**: The blocked-egress scenario is executed on the reference workstation and its result
  (pass or fail with details) is recorded, closing A-032 or documenting why it cannot close.
- **SC-005**: The injection-resistance and isolation gates each report their case counts and
  failure counts from real-model runs.
- **SC-006**: Performance is measured with at least 50 queries after warm-up, warm and cold
  separately, and each master §13.4 budget is marked pass or fail with the numbers.
- **SC-007**: The traceability checker passes in CI with every local requirement mapped.
- **SC-008**: The held-out suite is run three times with the locked configuration, and every run
  plus the spread is reported.

## Assumptions

- The reviewer for FR-006 is a human; the agent's case authoring is labelled "agent-authored,
  unreviewed". F008 is expected to end with human-judged gates `blocked`, which the F008
  acceptance explicitly allows.
- The reference workstation is the owner's machine with the local GPU; the corpus is the active
  snapshot (5 658 chunks), well below the 25 000-chunk qualification ceiling.
- SBOM generation and the portable release belong to F009; the release report links to the license
  inventory as it exists now.
- The offline check reads the installed model files read-only; it never pulls or modifies them.
